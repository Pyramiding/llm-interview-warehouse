# 07 · Agent、工具调用与自动化

> 本页 18 题是根据公开论文、官方协议与工程约束整理的**原创延伸题**，不宣称来自企业真实面试。核查截止 2026-10-22；论文的历史模型分数不能代表当前系统能力。协议选用明确版本，工程实现请锁定依赖与权限边界。

<a id="g01"></a>

### G01. 什么情况下应使用 Agent，什么情况下固定工作流更合适？

- **难度 / 适用岗位：**基础；应用开发、架构。
- **作答要点：**固定工作流用代码决定步骤，适合路径稳定、容易验证的任务；Agent 让模型依环境决定下一步，适合步骤难预先列尽的任务。[Anthropic 的工程文章](https://www.anthropic.com/research/building-effective-agents) 可用作架构分类参考。选择要看任务收益是否覆盖延迟、成本、失败恢复与权限成本，先用简单基线验证需要动态决策。
- **深入追问：**报销审核、代码修复、资料汇总分别哪些部分应固定？如何将一个失控 Agent 退回可控流程？
- **常见误区：**把有 LLM 的程序一律叫自主 Agent；用多 Agent 数量证明系统先进。

<a id="g02"></a>

### G02. ReAct 的核心闭环是什么，能解决与不能解决什么？

- **难度 / 适用岗位：**基础至中等；Agent 算法。
- **作答要点：**[ReAct](https://arxiv.org/abs/2210.03629) 将推理与环境动作交替组织，模型利用观察调整计划，而不是一次写完未经验证的方案。工程上保存状态、动作、参数和观察，便于重放；无需把模型内部推理全部暴露给最终用户。它仍会选错工具、误解观察和累积错误，需要外部验证、步数与成本上限。
- **深入追问：**观察过长如何压缩而不丢失失败原因？工具返回与模型预期矛盾时如何处理？
- **常见误区：**把一次有格式的“思考—行动”输出当成已完成动作；相信自述执行成功而不检查工具结果。

<a id="g03"></a>

### G03. 工具 schema 应怎样设计，为什么类型正确仍可能业务错误？

- **难度 / 适用岗位：**中等；应用开发、平台。
- **作答要点：**名称说明能力，参数给出单位、时区、枚举、必填字段与示例；输出提供结构化状态、结果与可恢复错误。schema 只保证格式约束的一部分，无法保证对象存在、金额合理或用户有权限。应用侧仍需校验 ID、前置状态、范围与授权，将含糊动作拆为可预览、可执行步骤。
- **深入追问：**“预订明天下午的会议”缺少哪些字段？如何避免模型将展示名称当作数据库主键？
- **常见误区：**将 JSON 合法等同于任务正确；工具描述过长但不写失败语义。

<a id="g04"></a>

### G04. Toolformer 与提示模型调用工具的区别是什么？

- **难度 / 适用岗位：**中等；Agent 研究、训练。
- **作答要点：**[Toolformer](https://arxiv.org/abs/2302.04761) 研究通过少量示范生成候选 API 调用，并根据对后续语言建模的帮助筛选训练数据；模型学习何时调用、参数和结果使用。提示方法主要在推理时提供接口与示例。不能把 Toolformer 等同于任意 function calling API；比较时应区分训练数据、工具执行正确性与最终任务成功率。
- **深入追问：**只用 next-token loss 改善筛选工具调用可能错过哪些有价值操作？如何生成不执行危险动作的训练数据？
- **常见误区：**认为模型生成函数名就有真实工具能力；忽略训练时工具输出与线上输出分布差异。

<a id="g05"></a>

### G05. Agent 记忆应该保存什么，如何避免记忆污染？

- **难度 / 适用岗位：**中等；Agent、知识系统。
- **作答要点：**区分当前工作状态、可验证事实、用户明确偏好、执行历史与任务经验；分别设置范围、有效期、来源、权限和删除机制。检索记忆时返回证据，不能把模型猜测直接晋升为用户事实。[Reflexion](https://arxiv.org/abs/2303.11366) 研究以文字反馈改进后续尝试，其记忆并非参数更新，也不保证反思一定正确。
- **深入追问：**同一用户在不同项目有冲突偏好如何存储？错误经验如何撤回并回归验证？
- **常见误区：**保存所有聊天作为“长期记忆”；把一次失败后的自我解释当作根因真值。

<a id="g06"></a>

### G06. 如何让 Agent 可靠地停止、请求澄清或升级人工？

- **难度 / 适用岗位：**中等；产品工程、平台。
- **作答要点：**定义完成条件、预算耗尽、不可恢复错误、缺少必要输入和高影响动作等终止状态；用外部状态机约束，不能只写“不要无限循环”。对重复动作、无新信息和工具错误设检测；澄清只针对影响决策的缺口，输出已完成内容与剩余阻塞。完成必须依据业务结果，例如对象创建后能回读，而非模型说“已完成”。
- **深入追问：**请求超时但远端可能成功，应停止、重试还是查询？哪些信息可用默认值补齐？
- **常见误区：**以 token 上限作为唯一终止机制；遇到所有不确定性都交给用户。

<a id="g07"></a>

### G07. 多 Agent 的收益、通信成本和失效模式是什么？

- **难度 / 适用岗位：**进阶；Agent 架构。
- **作答要点：**独立检索、不同专业审查等可并行任务可能获益；强依赖、共享同一资源的任务更易出现冲突。明确子任务输入、产物、所有权、证据格式和合并规则；子 Agent 应返回证据和限制，主 Agent 负责最终一致性。用相同成本预算比较单 Agent、并行采样和分工方案，不能把更多调用带来的收益都归因于协作。
- **深入追问：**两个 Agent 同时修改同一订单怎么办？主 Agent 如何发现子 Agent 的虚构引用？
- **常见误区：**多模型投票必然更正确；让所有角色自由聊天却没有可检查产物。

<a id="g08"></a>

### G08. Agent 评测为什么不能只看最终文本？

- **难度 / 适用岗位：**中等；评测、Agent 研究。
- **作答要点：**任务成功看环境状态是否满足目标，同时记录不必要动作、越权、成本、时延、可恢复性与副作用。[WebArena](https://arxiv.org/abs/2307.13854) 强调真实可复现环境，[AgentBench](https://arxiv.org/abs/2308.03688) 提供多类交互环境。评测需重置环境、锁定工具版本与随机种子，允许多条有效路径；把模型、编排和工具故障分开统计。
- **深入追问：**界面点击正确但订单没提交算成功吗？成功率如何按任务难度与重试次数分层？
- **常见误区：**用模型自评分作成功率；测试时残留上一轮环境改变。

<a id="g09"></a>

### G09. 编码 Agent 用 SWE-bench 时应注意哪些评价边界？

- **难度 / 适用岗位：**进阶；代码智能、评测。
- **作答要点：**[SWE-bench](https://arxiv.org/abs/2310.06770) 用真实仓库 issue 与对应修改构造任务；评测要说明具体子集、环境、工具、次数、token 预算和版本。测试通过是必要证据，但不能自动证明代码安全、可维护或覆盖所有真实需求；还需防止修改测试、跳过断言和借助泄漏补丁。历史论文分数只是历史基线。
- **深入追问：**pass@1 与 best-of-N 有何区别？测试环境无法复现时如何计分？
- **常见误区：**把不同子集的排行榜数字横向比较；把找到原 PR 的方案当独立解决。

<a id="g10"></a>

### G10. MCP 解决什么，不解决什么？

- **难度 / 适用岗位：**中等；平台、工具集成。
- **作答要点：**[MCP 2025-06-18 规范](https://modelcontextprotocol.io/specification/2025-06-18) 定义 host、client、server 与上下文/工具交互协议，涉及能力协商和 JSON-RPC。它改善集成方式的一致性，不自动赋予业务授权、模型准确性或端到端事务。面试中先说明协议版本，再谈工具发现、身份边界、超时、资源访问和审计；不要把协议名称当作安全保证。
- **深入追问：**同一个 MCP server 由不同用户访问，权限在哪里实施？资源与工具适合什么语义？
- **常见误区：**把 MCP 当模型或数据库；宣称接入一次即可安全访问全部组织数据。

<a id="g11"></a>

### G11. Agent 面对提示注入，如何区分指令和不可信数据？

- **难度 / 适用岗位：**进阶；安全、平台。
- **作答要点：**网页、邮件、检索材料和工具结果可能包含攻击文本，它们是任务数据，不应覆盖用户目标或授权。可信编排层实施工具白名单、参数校验、最小权限和敏感数据出口控制；模型层分类只能作为辅助。针对“读取内部文件并发送外部地址”等跨边界链路建测试，验证每个危险步骤能被独立阻止。
- **深入追问：**恶意页面伪称用户授权怎样处理？为何只删掉“ignore previous instructions”远远不够？
- **常见误区：**认为系统提示越长越安全；只评估显式攻击字符串而不评估间接工具链。

<a id="g12"></a>

### G12. 如何设计工具重试、幂等与补偿？

- **难度 / 适用岗位：**进阶；后端、Agent 平台。
- **作答要点：**先区分只读、可幂等写和不可重复副作用。网络超时不等于业务失败；使用客户端请求 ID、状态查询与去重，限定重试次数和退避。跨系统动作通常无法靠一次模型调用获得原子性，可用 saga 记录每步状态与补偿；补偿也可能失败，必须可见并支持人工恢复。
- **深入追问：**发邮件超时后能否直接再发？订票成功、付款失败时怎样恢复？
- **常见误区：**所有 5xx 都无限重试；认为模型能凭自然语言准确回滚外部世界。

<a id="g13"></a>

### G13. 定量推导：长任务的成功率为什么下降很快？

- **难度 / 适用岗位：**中等；算法、产品工程。
- **作答要点：**在“每步独立、任一步失败则全任务失败”的简化假设下，n 步成功率是 `p^n`。每步 p=0.98，30 步约为 54.5%；这不是生产预测，因为错误通常相关，且系统有恢复。启示是减少无价值步骤、对关键步骤加验证、保存检查点并支持局部重试；测真实任务级成功率校准模型。
- **深入追问：**若失败可被检测且最多重试两次，模型怎样修改？共享错误会如何破坏独立假设？
- **常见误区：**把公式结果当实测；以工具参数准确率代替整个任务成功率。

<a id="g14"></a>

### G14. 系统设计：做一个可执行企业工单的 Agent。

- **难度 / 适用岗位：**高级；架构、平台。
- **作答要点：**从工单读取、证据收集、方案生成、权限校验、执行和验收划分状态；为每个动作记录用户身份、资源、参数、前置版本与结果。权限引擎控制动作，审批与业务授权来自可信系统；外部写入使用幂等键。长期任务用持久化队列和事件恢复，任务结果需回读验收；评测覆盖缺权限、过期状态、重启、工具失败及恶意附件。
- **深入追问：**执行前资源被他人修改如何处理？怎样让暂停后继续时不重复写入？
- **常见误区：**将完整数据库凭据直接交给模型；只设计正常路径，没有失败状态。

<a id="g15"></a>

### G15. Agent 的延迟和成本怎样优化？

- **难度 / 适用岗位：**进阶；应用性能、平台。
- **作答要点：**拆分模型等待、工具等待、排队、序列化和重试；优化目标是每次成功任务成本与用户等待，不只是每 token 价格。独立只读查询可并发，重复上下文可缓存，确定性转换由代码处理，模型按任务难度路由。预算示例：10 次模型调用各 1.2 秒、串行工具累计 4 秒，理想下限约 16 秒，尚未计队列；仅把一个工具缩短 0.1 秒不会改变整体体验。
- **深入追问：**如何识别可并行操作？缓存工具结果如何考虑权限、时间与副作用？
- **常见误区：**只减少输出长度却不测任务成功率；并发依赖写操作导致状态竞争。

<a id="g16"></a>

### G16. 排障：Agent 一直调用同一工具，如何查？

- **难度 / 适用岗位：**进阶；Agent 工程。
- **作答要点：**检查调用是否真的成功、返回是否被截断、状态是否写回、错误码是否被误读为正常文本。比较重复参数、观察摘要与退出条件，重放最短失败轨迹。修复可能是明确结构化结果、把结果映射为状态、修正工具说明或增加无进展检测；再用一组循环案例回归。简单降低 temperature 不能修复状态机丢更新。
- **深入追问：**工具成功但业务状态未变化属于哪里？怎么区分必要轮询和无意义重复？
- **常见误区：**只把最大步数从 20 增至 100；没有保留失败时的工具返回。

<a id="g17"></a>

### G17. 排障：模型换代后工具调用率变高，但成功率变低，如何解释？

- **难度 / 适用岗位：**进阶；评测、MLOps。
- **作答要点：**分解为工具选择、参数、权限、调用时机、结果理解和终止判定；检查新模型的 schema 支持、序列化模板与工具描述兼容性。增加调用可能是有效探索，也可能是重复与错误恢复失效。固定任务集和预算，比较轨迹、成功率、成本分布并按工具切片；对高影响写入灰度并保持回滚。
- **深入追问：**总成功率持平、尾部延迟翻倍，是否可以上线？如何区分模型变化与工具服务退化？
- **常见误区：**将调用次数增长当能力提升；只看平均成本忽略失败任务的高消耗。

<a id="g18"></a>

### G18. 如何训练一个更会使用工具的模型？

- **难度 / 适用岗位：**高级；Agent 算法、后训练。
- **作答要点：**数据应覆盖正确调用、不调用、缺信息澄清、工具失败恢复和多轮验收；标签包含用户意图、可用权限、schema 版本与真实结果。SFT 学格式与策略，偏好或强化学习可优化任务收益，但奖励必须包含最终成功、成本及违规惩罚；防止刷工具、伪造观察和过拟合模拟器。以留出的工具、任务模板和时间切片检查泛化。
- **深入追问：**如何训练对新工具的适应能力？训练轨迹里错误动作是否全部删除？
- **常见误区：**只收集成功轨迹，导致不会恢复；只奖励最终文本好看而不核验环境状态。
