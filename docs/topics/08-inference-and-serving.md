# 08 · 推理优化、调度与在线服务

> 本页 18 题均为基于公开研究和系统约束原创构造的**延伸题**，并非企业真题。核查于 2026-10-22；`latest` 文档持续变化，实际部署应锁定版本、硬件与模型。所有数值算例均为明确假设下的练习，不是性能承诺。

<a id="i01"></a>

### I01. Prefill 与 decode 为什么瓶颈不同？

- **难度 / 适用岗位：**基础；推理、平台。
- **作答要点：**Prefill 一次处理多个输入 token，矩阵计算并行度较高；decode 自回归地产生新 token，常在小 batch 时受权重与 KV 数据移动限制。实际瓶颈取决于 batch、上下文、模型与硬件，长上下文 decode 也可能被 attention 或通信拖慢。用 kernel 时间、带宽、计算利用率和队列数据验证，不能仅凭阶段名判断。[FlashAttention](https://arxiv.org/abs/2205.14135) 提醒应关注内存层级与 IO。
- **深入追问：**高并发时 decode 一定是带宽受限吗？视觉编码阶段放在哪里观测？
- **常见误区：**将 GPU 利用率高等同于矩阵计算效率高；用单请求结果推断线上吞吐。

<a id="i02"></a>

### I02. TTFT、TPOT、ITL、吞吐量分别代表什么？

- **难度 / 适用岗位：**基础；服务工程、性能。
- **作答要点：**TTFT 是首 token 时间，受排队、预处理和 prefill 影响；ITL 是相邻输出 token 间隔；TPOT 常指首 token 后的平均每 token 时间，必须说明统计口径；吞吐量可按请求或 token 计。输入/输出长度分布、并发模型和采样设置需一起报告。p95 是请求分位数还是 token 分位数也需明示，不能混用。
- **深入追问：**吞吐量提高但用户更慢，可能发生什么？流式输出的总时延如何近似计算？
- **常见误区：**只报告 tokens/s；将离线批处理吞吐直接作为在线 SLO 能力。

<a id="i03"></a>

### I03. 定量推导：KV cache 显存如何估算？

- **难度 / 适用岗位：**中等；推理、架构。
- **作答要点：**普通 decoder、等长请求下，KV 字节约为 `2×L×B×S×H_kv×d_head×bytes`，2 对应 K 和 V。例：L=32、B=8、S=8192、H_kv=8、d_head=128、FP16=2 字节，约 8 GiB。另计权重、临时张量、CUDA graph、内存池和分页余量；不同请求长度用 `ΣS_i` 替代 B×S。[GQA](https://arxiv.org/abs/2305.13245) 改变 KV 头数；MLA 等架构需另建公式。
- **深入追问：**TP 分片后每卡 KV 是否总按 TP 等分？何种实现会复制 KV 头？
- **常见误区：**用 query 头数代替 KV 头数；以模型参数量直接推算长上下文并发。

<a id="i04"></a>

### I04. MHA、MQA、GQA 对推理有什么影响？

- **难度 / 适用岗位：**中等；模型架构、推理。
- **作答要点：**MHA 的每个 query 头有独立 K/V；MQA 共享一组 K/V；GQA 在两者之间共享多个 KV 组。KV 头更少通常降低缓存与读取压力，但模型质量、训练方式和并行映射需共同考虑。[GQA 原论文](https://arxiv.org/abs/2305.13245) 提出从多头 checkpoint 进行 uptraining 的方案；不能假定直接改配置就能保留质量。
- **深入追问：**H_kv 小于 TP degree 会怎样？为什么减少 KV cache 不一定同比减少总时延？
- **常见误区：**以为 GQA 减少 query 头数；只谈显存而不检查目标 kernel 是否支持。

<a id="i05"></a>

### I05. PagedAttention 解决什么，分页有哪些代价？

- **难度 / 适用岗位：**中等；推理系统。
- **作答要点：**[PagedAttention](https://arxiv.org/abs/2309.06180) 将逻辑连续的 KV 映射到可非连续的物理块，减少预留与外部碎片，支持共享。块表、分配器和间接访问有额外成本；块越大尾部内部浪费越大，越小管理与访存压力可能越高。它优化缓存管理，不会让 attention 的数学运算自动变成线性复杂度。
- **深入追问：**一个请求取消后哪些块能释放？共享前缀后新增 token 如何避免修改他人的缓存？
- **常见误区：**认为分页等于把 KV 放到 CPU；宣称“零碎片”而不区分内部与外部碎片。

<a id="i06"></a>

### I06. Continuous batching 与静态 batching 有什么区别？

- **难度 / 适用岗位：**中等；服务调度。
- **作答要点：**静态批次常等待整批完成；连续调度在迭代间插入新请求、移除完成请求，减少长短输出混合造成的空位。调度需同时约束 token 预算、KV 容量、公平性和延迟；最大 batch 并非唯一参数。观察负载下排队时间、活跃序列数和抢占率，理解调度策略的结果。[vLLM 调优文档](https://docs.vllm.ai/en/latest/configuration/optimization/) 可作具体实现参考。
- **深入追问：**大量短请求夹杂一个超长请求时如何避免饥饿？为什么 admission control 重要？
- **常见误区：**将无限增大并发视为免费吞吐；只测完成的请求，忽略超时和取消。

<a id="i07"></a>

### I07. Chunked prefill 如何平衡 TTFT 和输出流畅度？

- **难度 / 适用岗位：**进阶；推理调度。
- **作答要点：**将长输入的预填充分块，与 decode 共同调度，避免一次大 prefill 长时间阻塞已有流式输出。块大有利于计算效率，块小更利于交错与尾延迟，但带来调度开销。使用真实长度分布，联合测 TTFT、ITL、吞吐量和等待公平性；参数语义以所用版本的 [vLLM 调优文档](https://docs.vllm.ai/en/latest/configuration/optimization/) 为准。
- **深入追问：**同一 token 预算在短输入与长输入流量下为何效果不同？如何识别 prefill 抢占了 decode？
- **常见误区：**声称分块必然同时改善所有指标；拿离线最大吞吐代替在线体验。

<a id="i08"></a>

### I08. FlashAttention 为什么是 exact attention，为什么还能更快？

- **难度 / 适用岗位：**进阶；CUDA、推理算法。
- **作答要点：**[FlashAttention](https://arxiv.org/abs/2205.14135) 用分块和在线 softmax 避免把完整 attention 矩阵写入 HBM，保持相同数学 attention，浮点舍入仍可能不同。时间复杂度没有因此从平方变成线性。[FlashAttention-2](https://arxiv.org/abs/2307.08691) 进一步改善线程块和 warp 工作分配。面试应分清 IO、FLOPs、占用率与端到端收益。
- **深入追问：**在线 softmax 合并两个分块的最大值与归一化项如何写？短序列或小 head 场景为何收益可能小？
- **常见误区：**把 FlashAttention 当稀疏近似 attention；将 kernel 加速比直接乘到整体服务吞吐。

<a id="i09"></a>

### I09. Prefix caching 的命中条件和收益边界是什么？

- **难度 / 适用岗位：**中等；推理平台。
- **作答要点：**[vLLM 自动前缀缓存文档](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/) 说明复用共享前缀的 KV 可减少重复 prefill；通常不直接缩短新 token 的 decode。命中需 token 前缀及相关模型状态兼容，模板、空格、工具 schema 或 adapter 变化均可能破坏复用。缓存 key 还需考虑租户隔离与相关配置，评价时同时测命中率、节省的 prefill token 和显存挤占。
- **深入追问：**相同文本但不同 tokenizer 可共享吗？随机 nonce 放在 prompt 开头有何影响？
- **常见误区：**认为语义相近就能命中 KV；把 prefix cache 当作答案缓存。

<a id="i10"></a>

### I10. 推测解码如何做到加速而保持目标分布？

- **难度 / 适用岗位：**进阶；推理算法。
- **作答要点：**小模型先草拟多个 token，大模型并行验证；精确方案以一致的条件分布、采样变换（温度、截断等）和正确的接受/拒绝及残差重采样作校正，才保持目标采样分布；近似验证方案不能据此承诺保分布。[Leviathan 等](https://arxiv.org/abs/2211.17192) 与 [Chen 等](https://arxiv.org/abs/2302.01318) 给出两条经典研究线。收益取决于接受率、draft 成本、验证并行度和批量负载；高并发时收益可能下降。
- **深入追问：**接受概率中的 p/q 如何理解？贪心验证与随机采样为何实现不同？
- **常见误区：**承诺每次 token 完全相同；忽略不同随机数路径和浮点数值差异。

<a id="i11"></a>

### I11. 定量推导：推测解码的理想收益上限怎样估算？

- **难度 / 适用岗位：**进阶；推理性能。
- **作答要点：**假设接受率 α 独立、草稿长度 k，且全接受后再产出一个目标 token，每轮期望产出近似 `E=Σ_(i=0)^k α^i`（忽略上下文相关和实现细节）。k=4、α=0.8 时 E≈3.36；若 draft 与验证总耗时是普通单步 decode 的 1.8 倍，则理想加速约 1.87 倍。增加 k 的边际收益递减，真实值需测拒绝、缓存回退和调度开销。
- **深入追问：**为什么接受率 100% 也不意味着无限加速？如何为不同流量选择 draft 长度？
- **常见误区：**直接把 k 当加速倍数；不把 draft 模型占用的显存与 GPU 时间计入成本。

<a id="i12"></a>

### I12. Tensor parallel 与多副本部署如何选择？

- **难度 / 适用岗位：**进阶；架构、推理平台。
- **作答要点：**TP 将单模型层内计算分片，能容纳更大模型，但引入每层通信；多副本独立处理请求，适合模型单卡或单节点可放下时扩吞吐。先满足显存，再比较单请求延迟、互联拓扑、通信和副本利用率；跨节点 TP 尤其要测网络。增加 GPU 不保证降低每次成功请求成本。
- **深入追问：**同为 8 卡，TP=8 与两组 TP=4 的差异？KV cache 与权重瓶颈分别如何影响选择？
- **常见误区：**按卡数线性估算吞吐；不计通信拓扑和服务容错域。

<a id="i13"></a>

### I13. Prefill/decode 分离为什么可能有效，又为什么可能不划算？

- **难度 / 适用岗位：**高级；推理架构。
- **作答要点：**两个阶段资源特征和扩缩容需求不同，分开可减小干扰，但必须传输 KV、管理路由和故障恢复。收益取决于上下文长度、网络带宽、缓存格式兼容与队列状态。先建立单池最优基线，再测分离后的端到端 TTFT/ITL 与总成本，不能只比较单机计算耗时。此题为系统设计延伸，具体实现依赖所用运行时。
- **深入追问：**8 GiB KV 在有效 25 GB/s 链路上传输的理想下限是多少？约 0.34 秒，实际还需协议与竞争成本。
- **常见误区：**忽略 KV 传输；分离后仍按同一种指标扩容两个池。

<a id="i14"></a>

### I14. 系统设计：如何搭建有延迟 SLO 的多租户推理服务？

- **难度 / 适用岗位：**高级；服务架构。
- **作答要点：**先定义输入/输出长度、并发、优先级、模型及 SLO。网关负责鉴权、配额与流式连接；路由考虑模型、adapter、缓存和队列；worker 做 token 级调度、KV 管理和取消。提供长度上限、准入控制、过载拒绝、自动扩缩容和可回读的错误状态。按租户统计延迟、成功率与资源用量，演练 worker 故障与长请求洪峰。
- **深入追问：**排队超过预算时应继续等待还是拒绝？如何避免单租户长上下文耗尽 KV？
- **常见误区：**只部署一个推理进程并暴露端口；没有取消传播导致断开的请求继续消耗算力。

<a id="i15"></a>

### I15. 排障：显存还有空闲却 OOM，怎样定位？

- **难度 / 适用岗位：**进阶；推理运维。
- **作答要点：**区分权重加载、预热/图捕获、prefill workspace、KV 扩展和其他进程占用；检查申请的是连续大块还是缓存池预留，监测峰值而非只看故障后的快照。固定复现长度与并发，逐一降低 batch/token 预算，核对量化格式和并行配置。碎片、临时峰值与运行时预留均可能使“账面空闲”不等于可用。
- **深入追问：**为何减小最大上下文有时改善容量？为何 OOM 重启后短时间又正常？
- **常见误区：**仅盯权重大小；直接提高显存利用比例，挤掉临时张量空间。

<a id="i16"></a>

### I16. 排障：吞吐正常但 TTFT 或 ITL 尾延迟很差，如何排查？

- **难度 / 适用岗位：**进阶；性能、平台。
- **作答要点：**拆开网关、队列、tokenization、prefill、decode、网络发送；按输入/输出长度、租户、缓存命中和抢占切片。TTFT 异常优先看排队与大 prefill，ITL 抖动看调度干扰、KV 抢占、同步通信和客户端背压。用固定请求重放对比配置，确认瓶颈后再调分块与 token 预算。
- **深入追问：**服务端 token 已产生但客户端晚到是什么问题？p99 会被哪些低频事件支配？
- **常见误区：**只测 GPU kernel；以平均延迟正常否定用户尾延迟投诉。

<a id="i17"></a>

### I17. 为什么量化模型有时更慢？

- **难度 / 适用岗位：**中等至进阶；推理、压缩。
- **作答要点：**量化减小存储，不等于硬件能高效执行；解量化、重排、未融合 kernel、不支持的 shape 或回退路径可能抵消带宽收益。比较同硬件、同任务、同质量、同 batch 的 TTFT/TPOT，并检查实际 kernel 与 dtype；权重量化收益在小 batch decode 与大 batch prefill 可能不同。参见 [AWQ](https://arxiv.org/abs/2306.00978) 的算法与实现结合思路。
- **深入追问：**W4A16 与 W8A8 的计算路径有何区别？低比特是否能降低 TP 通信？
- **常见误区：**用磁盘文件大小推断速度；只报告量化后的最优场景。

<a id="i18"></a>

### I18. 如何提交可信的推理性能报告？

- **难度 / 适用岗位：**中等至高级；所有推理岗位。
- **作答要点：**记录模型 checkpoint、精度、框架/驱动、GPU 与互联、采样参数、长度分布、到达过程、预热和重复次数。区分冷启动与稳态、开放环与固定并发、缓存冷热；同时报告完成、失败、取消和超时。以满足 SLO 的 goodput 与每任务成本比较，不只选最大 tokens/s；公开压测配置和可复现小样本。
- **深入追问：**固定并发压测为何可能掩盖过载排队？输入吞吐与输出吞吐应该如何分别报告？
- **常见误区：**缺少长度口径；将论文中的特定硬件加速倍数写成自己环境的普遍结论。
