## 业务链路与阅读方式

先沿“数据与标签 → 表征/模型 → 候选与策略 → 在线执行 → 结果与反馈”定位瓶颈，再看评测、成本和失败恢复。每题可用一个真实但去标识的项目回答；没有线上实验时明确区分离线能力与业务增量。

## 系统链路：数据、基线、机制与验收

下表是可供面试设计的原创工程拆解；每个环节需用实际约束验证，不能由单个离线指标推断业务收益。

| 环节 | 数据 / 标签 | 传统基线 | LLM 结合机制 | 评测 / 成本 |
|---|---|---|---|---|
| 资格与身份 | 租户、用户身份、业务对象 | 鉴权、权限与规则服务 | 理解身份澄清语句，不自行授权 | 越权/串租户率；校验延迟 |
| 知识治理 | 政策版本、生效地区、证据 | FAQ、结构化规则、倒排 | 混合检索、重排、带证据生成 | 适用条款命中/事实正确；检索成本 |
| 意图与状态 | 用户陈述、确认槽位、历史动作 | NLU+状态机 | LLM理解改口、补槽和摘要 | 状态准确/回改一致；token与存储 |
| 规划与策略 | 业务前置条件、冲突、人工边界 | 流程编排、决策表 | 生成候选下一步，策略校验 | 合法转移与死循环率；轮数 |
| 动作执行 | 权限、确认、幂等、事务结果 | 工具网关与业务后端 | 受限参数生成、结果解释 | 错误动作/重复操作；工具p99 |
| 恢复与转人工 | 未知动作、超时、用户要求、队列 | 重试状态机、人工路由 | 证据摘要与接力信息整理 | 正确升级/重复解释；等待和人工分钟 |
| 训练与质检 | 证据问答、失败轨迹、人工裁决 | 规则检查、分类基线 | SFT、蒸馏、独立LLM裁判辅助 | 未见政策泛化/严重漏检；标注工时 |
| 上线评价 | 工单结果、重复联系、投诉、账单 | 随机实验、固定对照与回滚 | 失败聚类和回归集扩展 | 正确解决/错误动作/满意；每解决工单总成本 |

## 项目验收证据清单

提交设计或复盘时，至少准备以下可核查材料；不提供内部数据和个人信息。

1. 一个冻结政策版本与工具模拟器，给出目标状态、权限、错误动作及转人工定义。
2. 任务集包含正常、缺参、改口、政策冲突、重复请求、超时未知与跨租户攻击。
3. 同预算基线和检索/状态/执行消融，多次运行成功率及pass^k，注明模拟用户局限。
4. 去标识轨迹展示证据、确认、动作幂等、最终数据库状态及人工接力信息。
5. 上线以工单为单位报告重复联系、投诉、错误动作和总成本，列灰度停止与回滚条件。

### CS01. 客服系统为何不应只做一个问答 RAG？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。
- **原创作答要点：** 客服包含身份与意图确认、知识查询、槽位收集、业务动作、结果通知和转人工。FAQ/RAG 回答规则，状态机维护流程，工具服务执行授权动作；LLM 理解与表达需要受流程约束。分别定义回答正确、任务完成、错误动作与成本，先确定业务边界。
- **深入追问：** 退货政策回答对了却没有退货成功算完成吗？
- **常见误区：** 引用正确就认定服务闭环成功。
- **一手参考 / 适用边界：** [τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains](https://arxiv.org/abs/2406.12045)；参考其机制或评价框架，具体业务方案与阈值需另行验证。

### CS02. 知识库如何处理版本和适用范围？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。
- **原创作答要点：** 每条政策记录生效/失效、地区、产品、渠道、优先级和责任人；检索先按资格/时间过滤再相关性重排。保留证据版本供审计，历史订单可能适用旧规则，不能一律取最新；冲突与缺失转澄清或人工。答案生成不得补写没有证据的承诺。

### CS04. 知识问答和工具执行的训练标签如何不同？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。

### CS05. 工具调用如何防止重复退款和越权？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。
- **原创作答要点：** 权限与额度由服务端鉴权，模型只能提出动作；高风险步骤要求适当确认。幂等键绑定业务对象和操作意图，执行结果落事务状态，重试先查状态；超时区分未知与失败，不重复创建。输出给用户须以工具事实为准。
- **深入追问：** 请求超时但后台已成功怎么办？
- **常见误区：** 函数调用参数合法就等于有执行权限。
- **一手参考 / 适用边界：** [τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains](https://arxiv.org/abs/2406.12045)；参考其机制或评价框架，具体业务方案与阈值需另行验证。

### CS06. 客服项目怎样评价任务成功？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。
- **原创作答要点：** 比较目标状态与实际业务状态，检查政策和安全约束，失败动作不能被流畅回复抵消。按任务、难度和用户行为分层，使用多次重复评估稳定性；τ-bench 的 pass^k 关注多次都成功的可靠性，区别于 pass@k 至少一次成功。模拟用户不替代真实用户验收。
- **深入追问：** 十次有一次成功能称可靠吗？
- **常见误区：** 将 pass^k 和 pass@k 混用。
- **一手参考 / 适用边界：** [τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains](https://arxiv.org/abs/2406.12045)；参考其机制或评价框架，具体业务方案与阈值需另行验证。

### CS07. 转人工怎样优化而不是追求最低比例？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。
- **原创作答要点：** 定义必须转交的风险、权限、信息缺失与用户要求，路由带证据、已确认槽位和已执行动作。衡量解决率、重复解释、等待、转接准确和人工工作量；低转接率可能意味着困住用户。用分层阈值和人工反馈控制自动化边界。
- **深入追问：** 机器人不断澄清却不转人工怎么监测？
- **常见误区：** 把转人工视为模型失败而禁止。
- **一手参考 / 适用边界：** [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)；参考其机制或评价框架，具体业务方案与阈值需另行验证。

### CS08. 怎样做答案置信与拒答？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。
- **原创作答要点：** 分开检索证据覆盖、规则冲突、身份/槽位充分性和模型输出校验；模型自报置信不直接驱动动作。校准可测的判别信号，缺少关键事实先澄清；对无法证实内容返回有限答复并提供下一步。评估风险-覆盖曲线和不必要拒答。
- **深入追问：** 高相关文档却缺关键条款应该怎么答？
- **常见误区：** 向量相似度高即答案可信。
- **一手参考 / 适用边界：** [On Calibration of Modern Neural Networks](https://arxiv.org/abs/1706.04599)；参考其机制或评价框架，具体业务方案与阈值需另行验证。

### CS09. 客服中的提示注入为何可能来自知识库？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。

### CS10. SFT、偏好优化和规则系统各学什么？

### CS12. 客服质检标签如何避免循环自证？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。

### CS13. 情绪识别与安抚如何不越界？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。
- **原创作答要点：** 从用户明确表达识别投诉与紧急度，使用中性确认和可执行下一步，不编造同情经历或承诺。语气分类有不确定性，不能推断敏感状态；用户明确要求人工时遵守转接规则。盲评沟通质量之外检查是否掩盖事实、拖延或误导。
- **深入追问：** 礼貌回复但不给解决渠道怎样评分？
- **常见误区：** 安抚分高就替代问题解决。
- **一手参考 / 适用边界：** [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)；参考其机制或评价框架，具体业务方案与阈值需另行验证。

### CS14. 如何降低长会话上下文成本？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。
- **原创作答要点：** 结构化状态、证据引用和分层摘要替代重复粘贴全文，保留关键确认与动作审计。缓存键绑定租户、权限和政策版本，防止跨用户泄漏；短任务用轻模型，复杂争议升级。测成本-成功率曲线并检查压缩后遗漏否定、金额和条件。

### CS15. 线上灰度如何检验真实增量？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。
- **原创作答要点：** 按用户/工单随机分组防跨轮污染，预先定义观察窗和主要指标，分析重复联系与转人工成熟结果。先影子验证动作，再有限灰度，设置错误操作和隐私停止条件；排查分流不均、人工接力与节假日变化。线上收益需同服务质量与成本约束比较。
- **深入追问：** 复杂工单被更多转走导致机器人解决率升高怎么办？
- **常见误区：** 不控制工单难度就比较处理率。

### CS16. 多租户、多语言客服系统如何隔离？

- **难度 / 适用岗位：** 中高级至高级；客服应用算法、Agent 评测、业务系统。
- **原创作答要点：** 检索、缓存、工具凭据与日志都带租户及权限上下文，服务端强制校验而非依靠提示词。语言版本政策可能不同，先确认适用地区再生成；跨语言保持金额、日期和条款一致。构造越租户和混语言测试，隔离失败列为严重问题。
